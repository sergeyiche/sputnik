# Ревью качества и управляемости ответов «Спутника»

Дата: 17.11.2026. Объект: `apps/api`, `packages/rag`, `packages/skills`, `packages/dialogue`, `packages/knowledge`, данные тенанта `parkinson`.

## 1. Коротко

Главная проблема с врачами — не в модели и не в отсутствии данных. Это цепочка из трёх дефектов:

1. любая реплика короче 80 символов считалась уточнением предыдущей темы;
2. если модель-переписыватель возвращала самостоятельный вопрос без изменений, код считал это сбоем и приклеивал старую тему;
3. даже когда навык `find-doctor` срабатывал, «усиление поиска» подставляло первый чанк файла `Список врачей.txt`, а это только служебная шапка конвертера без единого врача.

В результате запрос «Подскажите контакты специалиста» уходил в тему лекарств, а в контексте оказывалась шапка файла. Модель честно отвечала «контактов нет». При запросе с городом семантический поиск случайно попадал в нужные строки — поэтому «с городом работает».

Дополнительно найден опасный дефект grounding: в сессии `7981f483…` на вопрос «Есть ли список врачей?» ассистент ответил «В Краснодаре…» и перечислил врачей из Пензы и Перми. Город был взят из памяти, а список — из нерелевантных чанков. Это хуже, чем «не знаю»: пользователь получает ложные контакты.

Часть дефектов исправлена в рабочем дереве (см. §5). Остальные рекомендации — в §6.

## 2. Как сейчас устроен ход диалога

`POST /v1/chat`:

1. `_prepare_turn` решает, уточнение это или новый вопрос (`is_followup`).
2. Для уточнения вызывается LLM-переписывание в самостоятельный вопрос (`resolve_turn`).
3. `apply_skills` маршрутизирует уже переписанный вопрос по эмбеддингам примеров domain-навыков.
4. `SkillTurn` добавляет тело навыка в system prompt, `query_hints` в поисковый запрос, `retrieval_boost` в контекст.
5. `RAGPipeline._retrieve` делает similarity search, затем добавляет чанки из `retrieval_boost`.
6. LLM генерирует ответ по контексту; citations нормализуются.

Слабые места этой схемы: шаг 1 слишком грубый, шаг 2 не различает «самостоятельный вопрос» и «сбой», шаг 3 зависит от качества переписывания, шаг 5 не умеет добирать данные по слоту (город) и не гарантирует полноту списка.

## 3. Разбор инцидента с врачами

### 3.1. Симптомы из БД

Сессия `34e9a63c-f98f-40e3-a6c8-f303386f6ea5`:

- пользователь: «Подскажите контакты специалиста»;
- ассистент: «В предоставленных документах контакты специалистов не указаны», `sources=[]`.

Сессия `7981f483-5db5-4a69-b04f-471ca7680b19`:

- пользователь: «Я живу в Краснодаре…»;
- затем: «Есть ли список врачей?»;
- ассистент: «В Краснодаре вы можете обратиться к… Колесова Татьяна Ивановна (Пермь), Князькина Юлия Александровна (Пенза)».

### 3.2. Причина №1: `is_followup` считал уточнением почти всё

`packages/dialogue/followup.py` (до правки):

```python
FOLLOWUP_MAX_LEN = 80
...
if len(text) < FOLLOWUP_MAX_LEN:
    return True
```

«Подскажите контакты специалиста» — 31 символ, значит уточнение. «Есть ли список врачей?» — 22 символа, тоже уточнение. Оба вопроса самостоятельные.

### 3.3. Причина №2: равенство ответа переписывателя трактовалось как ошибка

`resolve_turn` (до правки):

```python
if standalone.lower() == question.lower():
    return fallback_standalone(anchor, question), anchor or question
```

Если модель корректно возвращала самостоятельный вопрос без изменений, код приклеивал к нему старую тему. В сессии выше после темы «проверенный препарат» поисковый запрос становился «это проверенный препарат?\nПодскажите контакты специалиста», тема оставалась про препарат. `find-doctor` не срабатывал, retrieval искал лекарства.

Воспроизведение без GigaChat (LLM-эхо возвращает тот же текст):

```text
('это проверенный препарат?\nПодскажите контакты специалиста',
 'это проверенный препарат?')
```

### 3.4. Причина №3: boost подставлял служебную шапку

`RAGPipeline._retrieve` вызывает:

```python
boosted = self._vector_store.chunks_for_sources(missing, limit_per=1)
```

`ChromaVectorStore.chunks_for_sources` брал первый чанк источника. В коллекции `parkinson_kb` первый чанк `Список врачей.txt` (chunk_index 666) — это:

```text
# source-file: Список врачей.xlsx
# source-format: xlsx
# converted-at: 2026-09-13T09:51:19.636171+00:00
```

91 чанк файла, 77 городов, а в контекст при «усилении» попадала шапка. Модель не видела ни одного врача и отвечала «нет информации».

### 3.5. Причина №4: навык не просил город

`packages/skills/seeds.py`, `find-doctor` (до правки):

```text
- Не выдумывай телефоны и адреса. Если списка нет в контексте — скажи об этом.
```

То есть навык прямо предписывал сказать «нет информации». Механизма уточнения слота не было. Конфиг навыка содержал только `suggestions`.

### 3.6. Причина №5: память подставила город, а retrieval — чужих врачей

`packages/dialogue/memory.py` сохраняет город в той форме, в которой он был в реплике: `Краснодаре`, `Казани`. Затем `_attach_memory_facts` добавляет в system prompt «Город: Краснодаре». Модель видит город, но в контексте — случайные чанки списка (Пенза, Пермь). Вместо «в Краснодаре врачей в контексте нет» она подписала чужие строки Краснодаром.

Это дефект не только памяти, но и политики ответа: нет правила «город из памяти можно использовать только для фильтрации, а не для переименования чужих городов».

### 3.7. Почему с городом «работает»

Запрос «врачи в Краснодаре» семантически близок к строкам, где встречается «Краснодар». Top-k=5 обычно захватывает 1–2 таких чанка. Этого хватает, чтобы модель выдала 1–2 контакта. Но:

- в Краснодаре есть врачи минимум в трёх разных чанках (716, 735, 749);
- top-k=5 не гарантирует все три;
- модель не сообщает, что список неполный;
- возможны дубли (например, `Бриль Екатерина Витальевна` встречается дважды, `Артемова Наталья Сергеевна` — в Магнитогорске и Челябинске).

То есть «работает» = «иногда даёт часть списка», а не «даёт полный и корректный список».

## 5. Что уже исправлено в рабочем дереве

### 5.1. Follow-up и самостоятельные вопросы

`packages/dialogue/followup.py`:

- `is_followup` больше не считает длину единственным признаком. Учитываются анафора («это», «их», «там»), явные фразы («расскажи подробнее»), начало самостоятельного вопроса («что такое», «какие», «подскажите», «есть ли»). Порог сокращён до 18 значимых букв.
- `resolve_turn`: если LLM вернула тот же текст, это больше не «сбой». Для короткой реплики (<18 букв) она приклеивается к теме (это ответ вроде «Краснодар»), для длинной — считается самостоятельным вопросом.

Это устраняет и «контакты ушли в лекарства», и потерю темы после уточняющего вопроса.

### 5.2. Детерминированное уточнение города

Новый модуль `packages/skills/slots.py`:

- читает колонку «Город» из табличного файла навыка (`config.clarify.source`);
- нормализует падежи (`Краснодаре` → `Краснодар`, `Казани` → `Казань`, `Уфе` → `Уфа`);
- ищет город в текущей реплике и в памяти;
- если города нет — возвращает готовый уточняющий вопрос, не вызывая retrieval и LLM; если город назван одним словом и его нет в справочнике («Сочи»), это распознаётся как ответ, и ассистент честно говорит, что врачей из этого города в списке нет;
- если город есть — делает точную выборку строк этого города и формирует ответ детерминированно, без LLM. Это важно: маленькая модель упорно оставляла только строки, где в специализации есть «паркинсонолог», и теряла остальных врачей города. Детерминированный ответ перечисляет все строки (до `max_rows`, по умолчанию 30) и добавляет примечание, если список усечён;
- generic boost `find-doctor` при известном городе снимается, чтобы первым чанком не подставлялись врачи другого города.

`packages/skills/seeds.py`: у `find-doctor` появился `config.clarify` и правило «не отвечай “нет информации”, спроси город». `seed_parkinson_skills` умеет дописывать `clarify` и обновлять старый body, не затирая кастомные suggestions.

`apps/api/app/api/routes/chat.py`: уточнение обрабатывается до RAG и LLM, работает и для `stream:false`, и для SSE; обмен сохраняется в диалог, вопрос учитывается в usage. Для старых строк `find-doctor` без `clarify` действует встроенный fallback, поэтому поведение появляется без миграции БД.

### 5.3. Калибровка роутера навыков

Замеры на реальных эмбеддингах local e5 показали высокий baseline: «привет» — 0.818, «спасибо» — 0.844, «я живу в Казани» — 0.823. При пороге `0.42` это означало, что `find-doctor` и `medications` активны почти на каждом сообщении. Добавлено:

- provider-aware порог по умолчанию: `0.86` для `EMBEDDINGS_PROVIDER=local`, `0.42` для GigaChat;
- защита от старого `SKILLS_SCORE_THRESHOLD=0.42` при local: значение ниже 0.7 поднимается до 0.86 с предупреждением в лог;
- margin `0.04`: активируются только навыки, близкие к лучшему совпадению;
- `max_active` теперь действительно ограничивает число domain-навыков (раньше sticky могли раздуть список до 4);
- детерминированная активация по явным словам (`config.match_any`): «Какие врачи есть в Москве?» даёт score 0.850 — чуть ниже порога, но слова «врачи/невролог/контакты…» принудительно включают `find-doctor`. Это не даёт валидным формулировкам потеряться из-за калибровки порога.

`.env` и `.env.example`: переменная `SKILLS_SCORE_THRESHOLD` закомментирована, чтобы код выбирал порог по `EMBEDDINGS_PROVIDER` (local — 0.86, GigaChat — 0.42). После калибровки «привет», «спасибо», «я живу в Казани», «какая погода» не активируют ни один domain-навык; «какие упражнения» — только `exercises`, «есть ли список врачей» — только `find-doctor`, «побочные эффекты леводопы» — только `medications`.

### 5.4. Служебная шапка больше не попадает в индекс и в boost

`packages/knowledge/base.py`: `strip_conversion_header`, `is_conversion_header`.

`packages/etl/ingest.py`: перед чанкованием из документов удаляется `# source-file` / `# source-format` / `# converted-at`.

`packages/knowledge/chroma_store.py`:

- `similarity_search` перебирает с запасом и пропускает чанки, состоящие только из шапки;
- `chunks_for_sources` запрашивает больше кандидатов и пропускает шапку, поэтому boost отдаёт реальные строки.

Старый индекс можно не пересобирать для работы фильтра, но переиндексация нужна, чтобы убрать шапку физически.

- Ввести обязательное правило: «город из памяти можно использовать только для фильтра; если в контексте нет врачей этого города — скажи об этом, не подписывай чужие строки». В `find-doctor` это уже сделано детерминированной выборкой.
- Добавить политику small talk: реплика «Меня зовут Анна, я живу в Казани» не является вопросом, но retrieval находит врачей, и ассистент без запроса выдаёт список. Нужен признак «это не вопрос» → тёплый ответ, сохранить факт в память, не подмешивать retrieval.
- Убрать конфликт промптов: базовый промпт разрешает fallback по общим знаниям, а `find-doctor` запрещает. Нужна явная иерархия: safety → факты из КБ → навык → общий fallback.
- Включить `RAG_MAX_DISTANCE` или reranker, чтобы нерелевантные чанки не доходили до модели.
- Рассмотреть чанкование таблиц по строкам с сохранением заголовка, а не «800 символов с перекрытием».
- Добавить дедупликацию врачей по ФИО + контакту + городу.

### P1 — память и приватность

- Нормализовать город при извлечении, а не только при чтении (`Краснодаре` → `Краснодар`).
- Хранить провенанс факта (из какой реплики) и не использовать memory-город как доказательство наличия врача.
- Добавить TTL/очистку `dialogue_memories` и `chat_sessions`; сейчас `DELETE /v1/session` не удаляет историю.
- Проверить IDOR: `GET /v1/session` принимает произвольный `X-Session-Id` и отдаёт переписку в рамках тенанта. UUID трудно угадать, но при утечке ID данные доступны. Нужна подпись/ротация или привязка к сессии.

### P2 — эксплуатация

- `GET /v1/knowledge/status` и `/v1/knowledge/sources` используют глобальные `KNOWLEDGE_DIR`/`CHROMA_COLLECTION`, а не каталог активного тенанта. В кабинете организации это показывает чужой/устаревший путь.
- `docker compose --profile tools run ingest` индексирует `data/knowledge` в `parkinson_kb`, а не `data/tenants/parkinson`. Это может перезаписать актуальный индекс устаревшей копией. Нужно перевести скрипт на tenant-dir или запретить в пользу импорта из админки.
- В `tenants.prompt_path` у `parkinson` лежит `/www/oracool/...` — устаревший путь. Поле, похоже, уже не используется, но его стоит почистить, чтобы не путать операторов.
- Стриминг не учитывает токены; после фикса считает хотя бы вопросы и пустые retrieval. Для расходов нужен token usage и из стрима.
- В окружении выкатки убрать `[::1]` из `NO_PROXY`/`no_proxy`: `httpx` не парсит такую запись и падает с `Invalid port ':1]'` до любых сетевых вызовов.
- `is_suspicious_query` ловит подстроку `"system prompt"` в обычном вопросе. Стоит перейти на более аккуратные паттерны.

## 7. Минимальный план проверки после выкатки

1. Юнит-тесты: `pytest -q` (ожидаем 139 passed; `NO_PROXY` без `[::1]`).
2. Ручной сценарий на `parkinson`:
   - контакты без города → уточнение;
   - город → только этот город;
   - город из памяти → поисковый запрос содержит город;
   - «а дозировку?» после лекарств → тема сохраняется;
   - «Есть ли список врачей?» после лекарств → не уходит в лекарства.
3. Регресс цитат: в ответе по городу источники — `Список врачей.txt`, номера цитат не ссылаются на чужие документы.
4. Проверить, что boost не добавляет шапку: в `sources` нет пустого документа, в контексте есть ФИО.
