# Мультитенантность

Один процесс API обслуживает все организации. Какая из них отвечает на запрос, решает заголовок `Host`. Отдельного сервиса на организацию нет.

Базовый домен задаётся `PLATFORM_BASE_DOMAIN` (локально `spootnik.local`, на проде `spootnik.ru`).

## Адреса

| Хост | Что открывается |
|------|-----------------|
| `spootnik.ru`, `www` | Лэндинг: заявка и виджет организации `help`. Консоль оператора — `/console/` |
| `help.spootnik.ru` | Кабинет организации `help` (`/admin/`) и файлы виджета для лэндинга |
| `admin.spootnik.ru` | Переход на `spootnik.ru/console/` |
| `{slug}.spootnik.ru` | Страница организации. Виджет — после включения |
| `localhost`, `127.0.0.1` | Прежний режим без организации: общие каталоги `data/knowledge` и коллекция из `CHROMA_COLLECTION` |

Локально те же имена с доменом `spootnik.local` и портом виджета `8080`. Фонд уже работает на `parkinson.spootnik.ru`. Новый поддомен нужно добавить в `/etc/hosts` на `127.0.0.1` — маска `*` в этом файле не работает.

Nginx виджета смотрит на имя хоста. Корень домена отдаёт лэндинг и `/console/`. `help` с корня переходит в `/admin/`. `admin.{домен}` перенаправляет на корень `/console/`. Любой другой поддомен получает страницу организации: название, описание, цвет и юридический текст. Виджет на ней появляется только при статусе `active`.

## Как выбирается организация

`PlatformHostMiddleware` разбирает `Host` и кладёт результат в контекст запроса.

1. `localhost` и адреса тестов — режим `legacy`.
2. Корень домена и `www` — лэндинг.
3. `admin.{домен}` — запасной хост консоли оператора (браузер уходит на корень `/console/`).
4. Один уровень поддомена — организация с этим slug. `help.spootnik.ru` тоже организация, хотя slug `help` нельзя выбрать в заявке.
5. Всё остальное — неизвестный хост, чат отвечает 404.

Заявка принимается только с лэндинга. Консоль оператора (`/v1/platform/*`) открывается на корне домена, на `admin.{домен}` и в режиме `legacy`, не на `help`.

Slug — латиница, цифры и дефис, до 32 символов. Заняты `www`, `api`, `admin`, `app`, `mail`, `platform`, `static`, `widget`, `help`.

## Жизненный цикл

Статусы: `pending`, `active`, `rejected`, `suspended`.

1. Форма лэндинга вызывает `POST /v1/platform/register`: название, российский телефон (`+7` и 10 цифр) и почта. Письмо содержит ссылку `http://<домен>/onboarding/?token=…` на 24 часа. Пока заявка не закончена, ссылку можно открыть снова. Организация на этом шаге не создаётся.
2. По ссылке два шага. Сначала адрес латиницей и пароль кабинета: адрес резервируется. Затем название и описание шапки и цвет через `input type="color"`. После второго шага появляется организация `pending`: каталоги, копия `config/default_system_prompt.md` и настройки виджета. Поддомен сразу показывает страницу организации в её цвете. Чат на ней появляется только после включения.
3. Оператор на `/console` подтверждает заявку. Статус становится `active`, на странице появляется виджет.
4. Отклонение ставит `rejected`. Чекбокс включения переводит уже подтверждённую организацию между `active` и `suspended`.
5. Чат отвечает только при статусе `active`. Кабинет открыт у `pending`, `active` и `suspended`.

Телефон, почта и пароль владельца хранятся в `data/platform/platform.db` (хеш пароля и токена ссылки). Письмо со ссылкой уходит тем же способом, что и восстановление пароля. Почта обязательна. Если у владельца её не было, при открытии базы подставляется `{slug}@spootnik.local`. Локально письмо всё равно попадает в Mailcatcher (`http://localhost:1080`), настоящий ящик нужен только при `MAIL_TRANSPORT=mailtrap`. В `.env` остаются учётка оператора `ADMIN_USERNAME` / `ADMIN_PASSWORD`, ключ GigaChat и способ отправки: `MAIL_TRANSPORT=smtp` либо ключ Mailtrap.

На странице входа кабинета есть «Забыли пароль?». Письмо уходит только если почта совпадает с владельцем этого поддомена. Ссылка ведёт на `/admin/#reset=…` и действует `PASSWORD_RESET_TTL_MINUTES`. Повторный запрос гасит предыдущую ссылку.

Шаблон `config/default_system_prompt.md` содержит плейсхолдеры вроде `{{НАЗВАНИЕ_ОРГАНИЗАЦИИ}}`. Сейчас подтверждение копирует шаблон как есть. Организация правит текст во вкладке «Промпт». Подстановка значений из заявки в эти плейсхолдеры ещё не сделана.

## Что изолировано

| | Своё у организации | Общее |
|--|--------------------|--------|
| Файлы | `data/tenants/{slug}/` | — |
| Chroma | коллекция `tenant_{slug}` | один каталог Chroma на диске |
| Промпт | `prompt_default.md` и версии в `prompts/` | шаблон новой организации в `config/` |
| Сессия диалога | пространство имён по slug, заголовок `X-Session-Id` | — |
| Вход в кабинет | почта владельца, cookie на этот хост | — |
| GigaChat | учёт вопросов и токенов по организации | один ключ и одна модель |
| Примеры в виджете | таблица `starter_questions` | каталог JSON только в режиме без поддомена |

У фонда коллекция остаётся `parkinson_kb`, не `tenant_parkinson`.

Каталог организации:

```
data/tenants/{slug}/
  knowledge/            .txt для индекса
  knowledge_sources/    исходники pdf, docx, xlsx
  prompts/              state.json и versions/
  branding/
  prompt_default.md     текст кнопки «Восстановить промпт по умолчанию»
```

`data/tenants/` и `data/platform/` в git не входят. Импорт из кабинета индексирует `knowledge` этой организации в её коллекцию.

`./scripts/docker-ingest.sh` по-прежнему читает общий `data/knowledge` и пишет в `parkinson_kb`. Для фонда после переноса файлов источник — `data/tenants/parkinson/knowledge`.

## Два входа

Имя cookie одно: `oracool_admin`. Путь и хост разные, атрибута `Domain` нет.

| Кто | Где | Cookie |
|-----|-----|--------|
| Оператор платформы | `POST /v1/platform/login`, логин из `ADMIN_USERNAME` | путь `/v1/platform` |
| Владелец организации | `POST /v1/admin/login` на своём поддомене, почта и пароль из базы | путь `/v1/admin` |

Консоль оператора — `https://spootnik.ru/console/`: очередь заявок, включение организаций и расход GigaChat. Кабинет `help` на `help.spootnik.ru/admin/` такой же, как у любой другой организации.

## Виджет

Сниппет стоит на сайте организации и грузит скрипт со своего поддомена:

```html
<link rel="stylesheet" href="https://mycompany.spootnik.ru/widget/sputnik.css" />
<script src="https://mycompany.spootnik.ru/widget/sputnik.js" defer></script>
<sputnik-widget></sputnik-widget>
```

Запросы идут на origin скрипта, поэтому `Host` совпадает с организацией. Сессия передаётся заголовком `X-Session-Id`. Настройки внешнего вида и примеры вопросов хранятся в базе этой организации. `GET /v1/suggestions/starter` отдаёт не больше трёх случайных вопросов; если их нет, виджет не показывает блок примеров.

Лэндинг подключает виджет с `help.{текущий домен}`, чтобы ответы на корневой странице шли из базы `help`.

## База платформы

SQLite: `PLATFORM_DB_PATH`, по умолчанию `data/platform/platform.db`. В ней организации, владельцы, настройки виджета, примеры вопросов и суточные счётчики (вопросы, токены, пустые ответы, ошибки, 429 и 402). Тексты документов в базе не лежат.

Карточка ключа в консоли суммирует расход за 7 дней и запрашивает остаток кабинета GigaChat. Если API остатка недоступен, карточка пишет об этом и не роняет список организаций.
