# Двухслойная защита базы знаний

Черновик решения от 18.11.2026. Код пока не реализует эту схему; документ фиксирует контракт, чтобы правки `txt` не терялись при повторной конвертации источников.

## Проблема

Сейчас `knowledge/*.txt` — производный файл от `knowledge_sources/*`. Конвертер перезаписывает его, а админка не различает:

- файл, который только что получен из источника;
- файл, который вручную поправили после конвертации.

Из-за этого исправления OCR, опечаток, служебных блоков и формулировок могут быть потеряны при следующей конвертации. При этом исходные PDF/DOCX/XLSX мы не редактируем и не должны редактировать.

## Схема

```text
data/tenants/{slug}/
  knowledge_sources/      # неизменяемые оригиналы
  knowledge_generated/    # результат конвертера; всегда можно пересоздать
  knowledge/              # эффективные документы, которые индексируются; их можно править
  knowledge_versions/     # резервные копии txt перед перезаписью
  knowledge_meta.json     # хеши, состояния, автор/время правки
```

- `knowledge_generated/` — «черновик конвертера».
- `knowledge/` — «опубликованный» документ, который видит RAG.
- `knowledge_meta.json` — побочные метаданные, не попадает в индекс.

## Состояния документа

| Состояние | Условие |
|---|---|
| `generated` | `knowledge/` совпадает с последним `knowledge_generated/` |
| `edited` | `knowledge/` отличается от последнего сгенерированного, источник не менялся |
| `stale` | источник изменился, `knowledge/` не пересобирался |
| `edited+stale` | есть и ручные правки, и новый источник — опасный случай |
| `manual` | у `txt` нет источника (например, `parkinson-medications.md`) |

В таблице документов админки показываем бейджи: «Изменён вручную», «Источник обновился», «Конфликт».

## Конвертация

1. Конвертер пишет результат в `knowledge_generated/`.
2. Считаются:
   - `generated_sha256` — хеш тела сгенерированного документа;
   - `source_sha256` — хеш источника;
   - `content_sha256` — хеш текущего `knowledge/`.
3. Если `knowledge/` отсутствует — просто копируем generated в effective.
4. Если `content_sha256 == generated_sha256` — ручных правок нет; заменяем effective на generated и обновляем метаданные.
5. Если `content_sha256 != generated_sha256` — есть ручные правки:
   - effective **не трогаем**;
   - возвращаем предупреждение `document_edited`;
   - показываем, что изменилось (сначала хотя бы счётчик строк/байт, позже diff).
6. При выборе «Перезаписать»:
   - старый effective копируется в `knowledge_versions/YYYYMMDD-HHMMSS/`;
   - записывается generated;
   - метаданные обновляются.
7. «Конвертировать новые и изменённые» пропускает `edited` и `edited+stale`, перечисляет их в ответе.
8. Удаление источника:
   - если связанный `txt` не редактировался — можно удалить вместе;
   - если редактировался — отдельное подтверждение: удалить только источник / оставить `txt` / удалить оба.

## Почему хеши, а не mtime

`mtime` уже используется в `convert_pending` как грубая защита, но ему нельзя доверять:

- копирование/restore меняет время;
- `touch` меняет время без изменения содержимого;
- правка может сохранить старое время;
- разные ФС и монтирования ведут себя по-разному.

Хеш тела документа (без служебной шапки `# source-file…`) — надёжнее. Служебную шапку исключаем, чтобы изменение `converted-at` не выглядело ручной правкой.

## Предупреждение в API

Для одного файла:

```json
{
  "code": "document_edited",
  "document": "Список врачей.txt",
  "source": "Список врачей с сайта.xlsx",
  "state": "edited",
  "message": "TXT изменён вручную после последней конвертации. Конвертация перезапишет правки.",
  "options": ["cancel", "download_current", "overwrite_with_backup"]
}
```

HTTP `409 Conflict`, пока админ не подтвердит overwrite.

Для массовой конвертации:

```json
{
  "results": [],
  "skipped_edited": ["Список врачей.txt", "Навигатор по проектам фонда.txt"]
}
```

## UI (позже)

- Кнопка «Конвертировать» для `edited` открывает предупреждение, а не сразу пишет.
- Кнопка «Скачать текущий TXT» доступна из предупреждения.
- «Перезаписать» требует явного подтверждения.
- В списке документов — бейдж и дата правки.
- Редактор `txt`: сохранение с `expected_sha256`, чтобы не затереть параллельную правку; история версий; «сравнить с generated»; «сбросить к generated» с бэкапом.

## API редактора (позже)

| Метод | Назначение |
|---|---|
| `GET /v1/admin/documents/{name}` | Текст, метаданные, состояние |
| `PUT /v1/admin/documents/{name}` | Сохранить текст; `expected_sha256` для optimistic locking |
| `GET /v1/admin/documents/{name}/history` | Версии и бэкапы |
| `POST /v1/admin/documents/{name}/restore` | Восстановить версию |
| `GET /v1/admin/documents/{name}/diff` | Diff с `knowledge_generated` |
| `POST /v1/admin/documents/{name}/reset-generated` | Явный сброс к generated с бэкапом |

## Миграция текущих данных

1. Создать `knowledge_generated/` и скопировать туда текущие `knowledge/*.txt` как baseline (кроме `manual`-файлов).
2. Для каждого файла записать `generated_sha256 = content_sha256` на момент миграции. Это фиксирует текущее состояние как «сгенерированное», даже если в нём уже были ручные правки.
3. Дальнейшие изменения `knowledge/` будут отличаться от baseline и получат `edited`.
4. Для `manual`-файлов (`*.md` без `# source-file`) generated не создаётся.
5. Backup `knowledge/` перед миграцией обязателен.

## Что не делаем сейчас

- Не реализуем редактор `txt`.
- Не включаем автоматический merge прозы.
- Не меняем ingest: RAG продолжает читать `knowledge/`.
- Не трогаем исходные PDF/DOCX/XLSX.
